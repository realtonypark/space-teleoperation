# H20: Release-is-reset chaining with a slack tether

**Axis:** task and data design. **Author angle:** self-resetting microgravity task design (tethered objects, return mechanisms) to maximise demonstrations per hour.

## Claim

If task 2 is redefined so that every demonstration ends with a re-release that seeds the next demonstration (targets alternate A→B→A, no canonical initial state), and the object hangs on a slack tether that only acts outside the working volume, then gross demonstrations per hour (successes ÷ total wall time including resets) on `leo_relay` rises by ≥40 % over a baseline that restores the canonical spawn state by teleoperation, while success rate stays ≥90 % of the baseline's.

## Mechanism

The testbed's `demos_per_hour` charges only the successful episode (measured: 6.0 s at `zero`, 6.3 s at `leo_relay`, seeds 0–2, ≈600 demos/h) and resets for free because `sim.reset` teleports the box. In orbit nobody teleports it. Under the SYNTHESIS §5 baseline (no onboard autonomy that moves the arm) the canonical reset is itself a teleoperated carry: 0.22 m back to the spawn zone at 0.07 m/s, release near rest, retreat. That is 4–6 s at zero latency `[derived from the operator model]`, 70–100 % of the demonstration, and it inflates with latency like the carry (×1.45 at 250 ms RTT, teleop_fundamentals §1.2). Earth data agrees: ALOHA logged 10–20 min of data per 30–60 min of wall clock "because of resets and teleoperator mistakes" (https://arxiv.org/html/2304.13705); LeRobot defaults to `reset_time_s = 60` against `episode_time_s = 60` (https://huggingface.co/docs/lerobot/en/il_robots).

Chaining removes the reset segment by making each demonstration's terminal act the next initial condition, the forward/backward pairing of reset-free RL (Eysenbach et al. 2017, https://arxiv.org/abs/1711.06782; Gupta et al. 2021, https://arxiv.org/abs/2104.11203; EARL, https://arxiv.org/abs/2112.09605). SYNTHESIS §3 already defines task 2 as "capture and re-release" at ≤2–5 cm/s and ≤1 rad/s, so the release push is data, not overhead.

The tether bounds the failure tail. Today a bumped object drifts until `max_s` expires; in a cage it parks on a wall, often out of reach. A thread anchored at the workspace centre with 0.20 m of slack exerts zero force inside the working volume (verified: MuJoCo 3.13 dead-band tendon, `springlength="0 0.20"`, zero passive force at 0.10 m) and returns an escaping object at ≤ its exit speed. Phenomenon D (free 6-DoF body, unique_data_study §2) is untouched while the thread is slack; rows with tendon length > 0.20 m are flagged and excluded from the "free" subset.

## Expected effect (quantified)

Per-demo wall time, baseline = episode + teleop reset ≈ 6 + 5 = 11 s at `zero`; chained ≈ 6.5 + 1 s release = 7.5 s (moving target adds ~0.5 s). Predicted gross demos/hour: +45 % (range +25 to +65 %) at `zero`, `direct_gs` and `leo_relay`; the ratio holds because both segments inflate with latency. Success rate: −3 to −10 points at `leo_relay` (a 3 cm/s target instead of 1 cm/s adds ≈1 cm of overshoot per 333 ms loop against a 5 cm capture envelope). Failed-episode mean duration: −40 % with the tether (turnaround within ≈13 s instead of running to `max_s`). Bandwidth, effective latency, safety events: unchanged.

## How the testbed falsifies it

Profiles `zero`, `direct_gs`, `leo_relay`; seeds 0–19; `tau_h` 0.25 s; 20 chained episodes per run versus 20 canonical episodes with a scripted teleop reset charged to wall time; RTT sweep 0–1000 ms. Metric: `demos_per_hour_gross = 3600 · successes / Σ(episode + reset wall)` per data_pipeline §3.2. **Reject** if the chained design's gross demos/hour at `leo_relay` is < 1.10× the baseline's, or its success rate < 0.90× the baseline's, or any unsafe-motion event, or if chained SAL/LDLJ distributions are worse than the baseline's by more than the seed-to-seed spread (the release must not turn demonstrations into chases).

## Implementation sketch

A scene and metric change, not a control strategy: it cannot live in the Strategy hook because `ground_step` and `sat_step` see only setpoints and a buffer. It composes with any Strategy.

- `spaceteleop/sim/__init__.py`: tendon in the XML string (`stiffness` 0.005 N/m `[design choice]`, `damping` 0.01, `springlength="0 0.20"`), target sites A/B, a release that sets box velocity to the arm's plus a seeded 2–4 cm/s push, target swap without touching the box (~25 lines).
- `spaceteleop/ground/operators.py`: release phase after success; return-to-spawn phase for the baseline reset (~20 lines).
- `spaceteleop/metrics/__init__.py`: gross demos/hour including reset wall and failures (~5 lines).
- `spaceteleop/run.py`: `--task capture_chain`, `--reset teleop|free` (~10 lines).

## Cost / complexity

Engineering 5–7 h including the baseline reset model. Runtime: realtime, ~10 min per 20-episode run. Satellite side: nothing; the tether is a passive thread and respects the SYNTHESIS §5 (c) decision. Hardware: one 20 cm Dyneema or elastic thread per cell, negligible mass `[unverified]`.

## Risks and failure modes

- Thread wraps on the gripper or arm; MuJoCo tendons pass through geometry, so the sim understates this. Mitigate with a short thread anchored below the workspace.
- Non-canonical initial states blur success-vs-latency comparisons across profiles; report the initial-state distribution per run and seed the push.
- A real thread yanks rather than springs; return speed is ≤ exit speed either way.
- A baseline reset modelled too slowly inflates the gain; the reset operator must share the demo operator's speed and reaction delay.
- Spin above 1 rad/s after a bumped release could cost more success than predicted.

## Confidence

0.65 that gross demos/hour beats the baseline by ≥40 % on `leo_relay`: the reset segment is as long as the demonstration and chaining removes it outright; the uncertainty is the success cost of a moving target and how honestly the baseline reset is modelled.
